Week 0 — Building a lab that is safe to attack

This lab simulates LLMjacking: an attacker stealing cloud credentials to run expensive AI models at the victim's expense. Before writing a single detection, the environment itself had to be sound, because a lab with sloppy credential hygiene would undermine the whole premise.

Security decisions and rationale

The decisions matter more than the clicks. Each one below was a choice with a trade-off.

A dedicated email identity for the root user

Decision
A separate mailbox for the AWS root user, with its own two-step verification, backup codes stored offline, and recovery phone and email configured.
Why
The root email is the account recovery path. Whoever controls it can request a password reset.
Trade-off
A mailbox that is rarely opened can go dormant. Mitigated with forwarding to a primary inbox and a periodic sign-in reminder.

An offline password manager instead of a cloud one

Decision
KeePassXC, a local encrypted file, over cloud-hosted managers.
Why
In February 2026, researchers at ETH Zurich and USI published attacks against several major password managers under a malicious-server threat model. A local file removes that attack surface entirely.
Trade-off
Backups become my responsibility, handled with three copies: local, cloud (the file is encrypted, so this is acceptable), and the master passphrase on paper.

The second factor lives outside the vault

Decision
TOTP codes stay in an authenticator app, not in the password manager, even though the manager supports them.
Why
Storing both factors in one place collapses two-factor authentication back into one. Backup codes live in the vault, so losing the phone is still recoverable.

Root parked, IAM user for daily work

Decision
An IAM user with its own MFA handles everything; root is reserved for billing and emergencies.
Why
Root can do irreversible things: close the account, change its email, remove MFA. The worst outcome of a mistake as the IAM user is deleting resources Terraform can recreate.

No long-lived access keys, anywhere

The decision this project turns on

LLMjacking campaigns overwhelmingly begin with a leaked long-lived access key. Creating one for a lab about detecting exactly that would be self-defeating.

The CLI uses aws login (AWS CLI 2.32.0 or later), which exchanges a console sign-in for short-lived credentials. Verified with aws sts get-caller-identity.

A detail that comes back later

The returned UserId begins with AIDA, the prefix for an IAM user. AKIA identifies long-lived access keys and ASIA identifies temporary credentials. Detections filtering on AKIA alone are blind to attackers operating with temporary credentials, a known gap this lab will document rather than hide.

Free plan, and deliberately no AWS Organizations

Decision
Stay on the AWS Free plan and avoid enabling AWS Organizations.
Why
The Free plan cannot incur charges: consumption is drawn from credits, and when the plan ends the account closes rather than converting to pay-as-you-go.
Watch out

Joining or creating an AWS Organization automatically upgrades the account to the paid plan and expires the credits immediately.

Service Control Policies are therefore unavailable in this lab, so the preventive controls in the response phase use IAM quarantine policies instead. That is a realistic constraint anyway, since most small teams operate a single account.

Cost guardrails before the first workload

Decision
A $50 monthly cost budget with three alerts on actual cost at 10%, 40% and 100%, which is $5, $20 and $50, delivered by email and configured before any resource existed.
Why
A lab that invokes AI models is exactly the kind of workload where a mistake compounds quietly.

Build log

Account

  1. Created the AWS account with the dedicated email, account type Personal, support plan Basic, account plan Free.
  2. Assigned an MFA device to the root user. AWS requires root MFA to be registered within 35 days of first sign-in, so doing it immediately avoids hitting that deadline.
  3. Confirmed the root user has no access keys.
  4. Set the working region to us-east-1. The console defaulted elsewhere; us-east-1 was chosen because Amazon Bedrock offers the widest model availability there and most tooling assumes it.

Cost controls

  1. Billing and Cost Management, then Budgets, Create budget, Customize (advanced), Cost budget.
  2. Monthly recurring budget of $50, scoped to all AWS services.
  3. Three alert thresholds on actual cost at 10%, 40% and 100%, all notifying by email.
Known limitation

The budget should also filter charge type to exclude credits, so alerts reflect real consumption rather than the net after credits. On a brand-new account that filter is empty, because Cost Explorer has not ingested data yet. Tracked in open items.

Daily-use identity

  1. IAM, Users, Create user, with console access and a generated password.
  2. Attached AdministratorAccess, appropriate for a personal lab. Least privilege is applied where it matters here: the roles and policies the lab itself creates.
  3. Signed in through the account sign-in URL and assigned a second MFA device to this user.
  4. Renamed both authenticator entries to distinguish root from the IAM user.

What this demonstrates

Nothing here is exotic, and that is the point. It is the baseline a cloud security engineer is expected to establish before any workload exists.

Identity and access managementRoot and daily-user separation, MFA on every human identity, no long-lived credentials
Secrets managementOffline encrypted vault, factors kept separate, documented recovery path
Cost governanceBudget alerts configured before the first resource
Infrastructure as code readinessProvider pinning, tagging strategy, state files excluded from version control
DocumentationDecisions recorded with rationale and trade-offs, including accepted constraints and open gaps
Résumé line

Built a hardened AWS lab environment for a purple team detection project: MFA-protected identity separation, zero long-lived access keys with short-lived CLI credentials, an offline secrets vault and cost guardrails, documented as a reproducible runbook.
